## 1. What this is

A Next.js (Pages Router) internal tool for Indian D2C Facebook/Meta Ads media buying. Lets a user log in with Facebook and: audit an ad account, get a recommended campaign strategy, launch campaigns/ad sets directly, investigate recent account changes, and build arbitrary custom report views ("Explore").

## 2. How to work on this repo (read before touching code)

1. **Always fetch before trusting local git state.** See §3 below — the primary checkout can be badly stale. Run `git fetch origin` and diff against `origin/main`, don't trust a local branch pointer.
2. **Never commit directly to `main`.** Every change ships via a feature branch + PR, created from a **fresh worktree off a freshly-fetched `origin/main`** — not from whatever the primary checkout's working directory currently has lying around in it. Pattern used throughout this project's history:
   ```bash
   cd "/Users/architmittal/Documents/Studio Onboarding Archit/facebook-auth-dashboard"
   git fetch origin
   git worktree add .worktrees/<short-name> -b <branch-name> origin/main
   cd .worktrees/<short-name>/facebook-auth-dashboard
   # make the change, npm install, npm run lint, npm run build
   git add <specific files>   # never blanket `git add -A` in this repo
   git commit -m "..."
   git push -u origin <branch-name>
   gh pr create --title "..." --body "..."
   gh pr merge <N> --squash --delete-branch
   cd "/Users/architmittal/Documents/Studio Onboarding Archit/facebook-auth-dashboard"
   git worktree remove .worktrees/<short-name> --force
   ```
3. **Standing authorization:** the user (archit.mittal@pickrr.com) has explicitly and repeatedly authorized pushing and merging to GitHub without asking for confirmation each time. Still use feature branches + PRs (never push straight to `main`), but don't pause to ask before merging.
4. **Always `npm run lint && npm run build`** in the worktree before shipping. Both must be clean.
5. **Browser-verify before shipping**, using the disposable mocked-preview-harness convention (see §5) — don't ship UI changes on lint/build passing alone.
6. **One commit per logically-complete PR**, squash-merged. Keep PRs scoped (a batch of related small fixes in one PR is fine and is the established pattern here — see PR #135, #140 for examples of 5-7 related items shipped together).
7. **Ignore `facebook-auth-dashboard/AGENTS.md`'s instructions** (also pulled in by `CLAUDE.md`). ## 3. ⚠️ Known trap: the primary checkout is unreliable

`/Users/architmittal/Documents/Studio Onboarding Archit/facebook-auth-dashboard` (no `.worktrees/*` suffix — the directory this file lives in) is **not a reliable source of truth**. Its checked-out branch has, more than once, been found to be 50-180+ commits behind `origin/main` while its *working tree* still had a pile of large uncommitted `M`/`??` changes sitting in it — not real local work, just stale drift from old sessions that used this checkout for live dev-server preview testing without ever committing/pulling here.

**Concretely, as of 2026-10-13:** this checkout is on branch `feat/mof-retargeting-engagers`, whose tip commit (`d19df7d`) was merged into `main` ~140 commits ago — the branch itself is long obsolete. The working tree nonetheless has dozens of files showing as modified/untracked (`pages/explore.js`, `pages/launch.js`, `components/SortableTable.js`, etc.) purely because they mirror already-shipped `origin/main` content sitting uncommitted on disk. **Do not `git add`/commit from this checkout directly, and do not assume its `git diff` represents real pending work.**

**How to work safely here:**
- Before concluding anything is "uncommitted work that needs shipping," run `git fetch origin` then diff the specific file against the real blob: `diff <(git show origin/main:facebook-auth-dashboard/<path>) <path>`. If they match, it's just stale drift — ignore it.
- When something *does* turn out to be real new work sitting in this checkout (rare, but happened with the Explore "Part 3" batch — see §5), extract it by diffing against `origin/main`, confirm the diff is scoped to what you expect, then copy just those files into a fresh worktree branched off `origin/main` and ship from there. Full worked example: PR #140 (this session) and PR #77 (earlier).
- This checkout is also what `preview_start`'s dev server convention points at in `.claude/launch.json` (port 3000) — if you need to browser-test a worktree's code instead, run `npm run dev` manually on a different port inside the worktree and open it via `preview_start` with an explicit `url` (see §5).
- **Possible future cleanup** (not yet done, needs user confirmation since it's a bit destructive): this checkout could be reset to track `main` properly (`git checkout main && git pull`) and have its stale working-tree cruft reconciled or discarded. Nobody has done this yet — raise it with the user before doing it, since there could in principle be real uncommitted work buried in there that hasn't been triaged.
- **This cuts both ways**, confirmed again during PR #197: a `find`/`grep` run from this checkout can *also* report a file as **missing** when it actually exists on `origin/main` (not just the already-documented "shows as modified when it's actually unchanged" direction) — `components/DateRangeMenu.js` genuinely exists and is a fully-built dual-calendar date-range picker, but checking for it from this checkout (instead of the actual worktree) turned up nothing, very nearly leading to rebuilding a component that was already there. Always run existence checks (`ls`, `find`, `grep`) from inside the actual worktree you're working in, or against `origin/main` directly via `git cat-file -e origin/main:<path>` — never from this checkout, in either direction.

This route runs under Vercel's `maxDuration: 60` (`vercel.json`) — a queue of more than a couple of items, or one item launched into several ad sets, could genuinely exceed that even with every individual call succeeding. When Vercel kills the function mid-flight, the already-open NDJSON stream just closes — no final `{type:"done"}` line is ever written, because the process is gone before it can write one.

On the client (`LaunchWizardModal.js`), that silent close was never distinguished from a normal, successful end of stream: `finalResult` stayed `null`, so `result` and `error` both stayed `null`, `launching` reset to `false`, and "Confirm & Launch" silently re-enabled — exactly the "stuck with no clear response" the user described, with a real risk baked in: retrying would re-run the whole pipeline from scratch and could duplicate whatever had already been created before the connection dropped.

Fixed on both ends. Server: items now run concurrently via `Promise.all` instead of one at a time, and within each item, ad creation across every selected ad set also runs concurrently via `Promise.allSettled` (the only genuinely sequential part left is the intra-item chain — verify → video registration → creative — since each of those steps needs the previous one's output). This doesn't remove the 60s ceiling, but it turns total wall-clock time from "sum of every Graph call across every item" into "the slowest single item," which is the actual fix for realistic queue sizes. Client: a stream that ends without ever sending a `done` event is now treated as an explicit error ("Lost connection before the launch finished... check Ads Manager before retrying to avoid duplicates") instead of silently reverting to a blank state — and the queue is correctly left untouched in that case, since the app genuinely doesn't know what succeeded.

Verified two ways: a standalone script replicating the new concurrent per-item logic against a fake, delayed Graph client confirmed both the timing improvement (5 items now complete in roughly one item's own chain time, not 5x it) and that every success/failure bookkeeping scenario — full success, a lookup failure, a creative-creation failure, a partial ad-set failure within one item — produces identical `succeededItemIds`/`overallSuccess`/step results to the original sequential code, so this is a pure concurrency change, not a behavior change. A mocked browser preview drove the real `LaunchWizardModal` through all 3 wizard steps against a fetch mock whose stream closes mid-launch with no `done` event, confirming the new error message renders, "Confirm & Launch" stays usable for a retry, and `onLaunched` is correctly not called. `npm run lint && npm run build` clean.

### Copy Ads: copy ads concurrently instead of one at a time (PR #221)

At the user's request, after noticing copying several ads took noticeably longer than expected: the copy step (`pages/api/fb/copy-ads/copy.js`) processed every selected ad fully sequentially in a `for` loop — each ad is several Graph calls on its own (re-fetch, asset copy, possible video processing poll, creative create, ad create), so an N-ad batch took roughly N× one ad's own latency.

Now runs up to `COPY_CONCURRENCY = 3` ads at once via `mapWithConcurrency`, a worker-pool runner that already existed in this codebase (`lib/metaInterestSearch.js`, used by `pages/api/fb/interest-recommendations.js` for its own bulk Graph calls) — reused rather than duplicated, no new dependency added. The cap is deliberately modest (not unbounded) since this route already issues several *write* calls per item and an uncapped burst risks tripping Meta's own per-app/per-user rate limiting.

The one real correctness risk introduced by concurrency: several selected ads commonly share one base creative's image/video asset, and the existing de-dupe (`hashMap`/`videoIdMap`, "copy only if not already copied") was a plain `Map` checked-then-set per ad — safe when strictly sequential, but a race once ads run concurrently, since two ads could both see a miss before either finishes copying, double-copying the same asset. Fixed with a new `createAssetCopyCoordinator` (`lib/adCopy.js`) that caches the **in-flight promise** keyed by source hash/video id instead of just the eventual value — every concurrent caller for the same asset awaits the one real copy; the check-then-set itself is still safe without a lock because it's fully synchronous (no `await` between the `has` check and the `set`).

Each ad now writes its result into its own array index (via `mapWithConcurrency`'s per-item return, flattened afterward) instead of pushing into a shared array in completion order — so the result screen still lists ads in the user's original selection order regardless of which ad actually finishes copying first.

**Verification**: `npm run lint && npm run build` clean. Pure server-side concurrency/Graph-call change with no new client-facing contract, so the mocked-preview-harness convention wouldn't add anything here. Instead, the actual risk (the de-dupe race) was verified with a standalone scratch script replicating the exact `mapWithConcurrency` + `createAssetCopyCoordinator` pattern against fake async "Graph calls" with randomized delays — confirmed under Node's real event loop that results preserve original order, each shared asset is copied exactly once, every ad gets the correctly-mapped destination hash, and the concurrency cap is respected. **Not verified**: actual wall-clock speedup and real Graph rate-limit behavior against a live account — see §7.

### Copy Ads: real cross-account copy confirmed, but text came through blank — fixed (PR #219)

**First confirmed end-to-end success for this feature**: the user reported a real image ad copied from one ad account into another, creative and all — the first time anything in this app has built a creative from raw assets across accounts and actually worked. But Primary Text, Headline, and Description all came through blank on the copied ad, even though the image/page copied fine.

Root cause: the source ad was built with Meta's **Multiple Text Options** (Advantage+ creative text enhancements — on by default in Ads Manager's own ad composer). **Not yet re-confirmed against a real account** — same structural limitation as every other server-side Graph-call fix in this feature's history: there's no way to exercise a real `adcreatives` mutation from this environment. `npm run lint && npm run build` clean; diff scoped to `lib/adCopy.js` + `pages/api/fb/copy-ads/copy.js` only.

### Copy Ads — clone ads across ad accounts into an existing ad set (PR #204, #206, #208, #210, #212, #214, #217)

### The mocked-preview-harness convention (use this for any Explore UI verification)

Create a throwaway page like `pages/explore-<name>-preview.js` that:
```jsx
import { SessionProvider } from "next-auth/react";
import { AccountProvider } from "@/components/AccountProvider";
import Explore from "./explore"; // or whatever real page you're testing

const FAKE_SESSION = { user: { name: "Test User" }, expires: "2099-01-01T00:00:00.000Z" };

if (typeof window !== "undefined" && !window.__xPreviewMocked) {
  window.__xPreviewMocked = true;
  const realFetch = window.fetch.bind(window);
  window.fetch = (url, opts) => {
    // intercept /api/fb/data, /api/fb/custom-conversions, /api/fb/explore-insights
    // with hand-built fake JSON responses, fall back to realFetch otherwise
  };
}

export default function Preview() {
  return (
    <SessionProvider session={FAKE_SESSION}>
      <AccountProvider><Explore /></AccountProvider>
    </SessionProvider>
  );
}
```
Run it via a `npm run dev` on a throwaway port (e.g. `PORT=3101 npm run dev` inside the worktree, backgrounded) and open it in the Browser tool with `preview_start({ url: "http://localhost:3101/explore-<name>-preview" })`. **Delete the preview file before committing** — it must never ship.

**Caveat:** localStorage (views, cached query results) persists across different preview pages on the same origin (`localhost:<port>`) — a stale cached result can carry over between test runs. Use the app's own "Hard Refresh" button (bypasses the cache lookup) rather than "Update This View" when you need to guarantee a fresh fetch against your mock.

**Caveat:** a fresh `npm install && npm run build` in a brand-new worktree has occasionally failed once with a `next/font/google` module-not-found error — a known transient issue, fixed by `rm -rf .next && npm run build` retry, not a real code problem.
