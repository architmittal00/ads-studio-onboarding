## 2. How to work on this repo (read before touching code)

1. **Always fetch before trusting local git state.** See §3 below — the primary checkout can be badly stale. Run `git fetch origin` and diff against `origin/main`, don't trust a local branch pointer.
2. **Never commit directly to `main`.** Every change ships via a feature branch + PR, created from a **fresh worktree off a freshly-fetched `origin/main`** — not from whatever the primary checkout's working directory currently has lying around in it. Pattern used throughout this project's history:
   ```bash
   cd "/Users/architmittal/Documents/Studio Onboarding Archit/facebook-auth-dashboard"
   git fetch origin
   git worktree add .worktrees/<short-name> -b <branch-name> origin/main
   cd .worktrees/<short-name>/facebook-auth-dashboard
   # make the change, npm install, npm run lint, npm run build
   git add <specific files>   # never blanket `git add -A` in this repo
   git commit -m "..."
   git push -u origin <branch-name>
   gh pr create --title "..." --body "..."
   gh pr merge <N> --squash --delete-branch
   cd "/Users/architmittal/Documents/Studio Onboarding Archit/facebook-auth-dashboard"
   git worktree remove .worktrees/<short-name> --force
   ```
3. **Standing authorization:** the user (archit.mittal@pickrr.com) has explicitly and repeatedly authorized pushing and merging to GitHub without asking for confirmation each time. Still use feature branches + PRs (never push straight to `main`), but don't pause to ask before merging.
4. **Always `npm run lint && npm run build`** in the worktree before shipping. Both must be clean.
5. **Browser-verify before shipping**, using the disposable mocked-preview-harness convention (see §5) — don't ship UI changes on lint/build passing alone.
6. **One commit per logically-complete PR**, squash-merged. Keep PRs scoped (a batch of related small fixes in one PR is fine and is the established pattern here — see PR #135, #140 for examples of 5-7 related items shipped together).

## 5. Most recent work (2026-10-16)

### Copy Ads — clone ads across ad accounts into an existing ad set (PR #204, #206, #208, #210)

New tab for a common D2C-agency pattern: the same Page running ads out of several ad accounts. Pick ads already running in one ad account, pick a destination ad account + an **already-existing** ad set in it, and the ad's creative (plus a new Ad pointing at it) gets rebuilt there. Deliberately scoped as a creative+ad clone, not a campaign/targeting migrator — the destination ad set's own budget/targeting are never touched, which sidesteps the much harder problem of mapping custom audiences/pixels/geo-targeting across accounts. Page and Instagram actor carry over completely unchanged (the feature's own premise is that the Page is identical across both accounts).

This is the first place in the app that builds a standard `object_story_spec` creative from raw assets instead of reusing an existing `creative_id` by reference — every prior "duplicate an ad" path (`pages/api/fb/duplicate-ad.js`, the Launch tab's own duplicate flow) explicitly avoids re-deriving a creative's full spec, since a creative is a standalone Graph object normally just referenced by id. That shortcut doesn't work across ad accounts (a `creative_id` can't be referenced from a different account), so this had to actually rebuild one. New `lib/adCopy.js`: images copy via Meta's own cross-account `copy_from` mechanism on `/adimages` (confirmed via Meta's reference docs — the account making the call just needs read access to the source account's creatives, which the user's own token already has); video has no `copy_from` equivalent, so it's re-ingested via `file_url` pointed at the source video's own `source` download URL, with a short bounded poll for Meta's async processing before the creative references it. Catalog/DPA ads (`product_set_id`) and Dynamic Creative ads (`asset_feed_spec` only) are detected up front (`classifyAd`) and shown disabled with a reason in the ad picker, rather than selectable and only failing later. Image/video assets are de-duplicated across an entire copy batch, not re-copied per ad, when several selected ads share the same creative asset. Same two-phase safety pattern as every other launch flow in this app: every created ad is `PAUSED` first, only flipped to `ACTIVE` in one final step and only if the whole batch succeeded.

**Real bug caught and fixed during mocked-preview verification** (same class as Partnership Ads' `BulkPermissionModal` bug one round earlier): the result screen briefly showed "1 of 0 ads created" instead of "1 of 2" — `CopyAdsModal` read `ads.length` live off a prop that the parent page shrinks (clearing the selection) the moment a copy succeeds. Fixed by snapshotting the selected ads once at mount via `useState(adsProp)` instead of reading the live prop throughout the component's life.

**PR #206, found on the first real-account try:** the source ads picker's account-wide `/ads` pull (no filtering at all, plus a fields string deep enough to include carousel `child_attachments`) tripped Meta's real `"Please reduce the amount of data you're asking for"` error — the one gap mocked-preview testing structurally can't catch, since a hand-built mock has no real row-count/response-size limit to violate. Fixed (incompletely — see PR #210 below) by adding a "Only show ads active in" date-range control (`lib/dateRanges.js`'s existing presets, originally defaulting to Last 90 Days) wired to `time_range`, believed at the time to be a real row-filter on the `/ads` edge itself per Meta's own reference page.

**PR #208, same real-account session, two more issues:** (1) narrowing the range and re-trying auto-fired the request again instantly (the fetch was in a `useEffect` keyed on account/range), with no way to adjust both before it fired — replaced with an explicit **Load Ads** button, and the default range narrowed 90 → 7 days (both requested directly and because a shorter default is itself less likely to trip the data-size error). (2) A second, worse crash: `Unexpected token 'A', "An error o"... is not valid JSON` — both the source-ads and `adsets-list` client fetches did a plain `res.json()`, which throws that exact opaque error the instant the server returns something non-JSON (a Vercel crash/timeout page) instead of this app's own `{error}` shape. Fixed with this project's own `lib/fetchJson.js` (`fetchWithTimeout` + `parseJsonResponse`) — the identical fix already applied to `pages/recent-changes.js` for the same crash shape (see PR #181 in the archived history below). Switching the source account now also resets the loaded ads/selection immediately so a stale list from a previous account can't be left on screen looking current.

**PR #210, correcting PR #206's own fix:** the "reduce the amount of data" error came back as `FUNCTION_INVOCATION_TIMEOUT` instead, on a busier account, even at the narrowed 7-day default. Root cause: `time_range`/`date_preset` on `GET /{accountId}/ads` **do not filter which ad rows come back at all** — they only scope nested insights-shaped sub-fields requested in the same call, a genuine gotcha this project's own earlier research (confirmed against Meta's reference docs) missed, since the docs page lists the param with no such caveat. PR #206's fix happened to dodge one error, probably by changing the declared query's estimated cost rather than its actual size, but the picker was still walking the account's **entire, unfiltered** ad list the whole time. Real fix in `lib/adCopy.js`'s `fetchCopyableAds`: ask `/insights` (which genuinely does respect `time_range` — the same mechanism `pages/api/fb/adsets-list.js` already relies on) which ad ids had real delivery in the window, then fetch the heavy per-ad fields only for that bounded set via the same chunked `?ids=`-batch-of-50 pattern `lib/adCreativeDetails.js`'s `fetchAdDetails` already uses. `since`/`until` are now required server-side (400 if missing). Trade-off, stated in the UI tooltip: a brand-new ad with zero spend/impressions yet won't show up until it has some — there's no other way to get a genuinely server-side-bounded "recent ads" list on this API. Relabeled the control "Only show ads with spend in" accordingly.

Verified via disposable mocked-preview harnesses (deleted before each commit): source account → ads table with Catalog/Dynamic Creative ads correctly shown disabled → multi-select → destination account + ad set picker → review screen (default `" - Copy"` names, Paused default) → confirm → NDJSON progress → result screen, including a deliberately-failing mock item to confirm failure rendering; separately, a simulated non-JSON 500 response confirmed to render as a clean readable error instead of crashing, and confirmed nothing fetches until Load Ads is clicked. **PR #210's own fix could not be verified this way at all** — the mocked-preview technique only ever intercepts calls from the browser to this app's own API routes, never the real Graph calls made inside them server-side, so it structurally cannot confirm whether `/insights` + chunked `?ids=` actually behaves as expected; only the unchanged client-facing contract was checked. `npm run lint && npm run build` clean on every PR.

**Never run against a real account** — see §7. The two steps with the least direct precedent in Meta's own docs (flagged in `lib/adCopy.js`'s own comments): whether `copy_from.source_account_id` wants the `act_`-prefixed id (this app's convention, sent first) or a bare numeric one, and whether the video-processing poll's `video_status` field values are read correctly.

### The mocked-preview-harness convention (use this for any Explore UI verification)

Create a throwaway page like `pages/explore-<name>-preview.js` that:
```jsx
import { SessionProvider } from "next-auth/react";
import { AccountProvider } from "@/components/AccountProvider";
import Explore from "./explore"; // or whatever real page you're testing

const FAKE_SESSION = { user: { name: "Test User" }, expires: "2099-01-01T00:00:00.000Z" };

if (typeof window !== "undefined" && !window.__xPreviewMocked) {
  window.__xPreviewMocked = true;
  const realFetch = window.fetch.bind(window);
  window.fetch = (url, opts) => {
    // intercept /api/fb/data, /api/fb/custom-conversions, /api/fb/explore-insights
    // with hand-built fake JSON responses, fall back to realFetch otherwise
  };
}

export default function Preview() {
  return (
    <SessionProvider session={FAKE_SESSION}>
      <AccountProvider><Explore /></AccountProvider>
    </SessionProvider>
  );
}
```
Run it via a `npm run dev` on a throwaway port (e.g. `PORT=3101 npm run dev` inside the worktree, backgrounded) and open it in the Browser tool with `preview_start({ url: "http://localhost:3101/explore-<name>-preview" })`. **Delete the preview file before committing** — it must never ship.

**Caveat:** localStorage (views, cached query results) persists across different preview pages on the same origin (`localhost:<port>`) — a stale cached result can carry over between test runs. Use the app's own "Hard Refresh" button (bypasses the cache lookup) rather than "Update This View" when you need to guarantee a fresh fetch against your mock.

**Caveat:** a fresh `npm install && npm run build` in a brand-new worktree has occasionally failed once with a `next/font/google` module-not-found error — a known transient issue, fixed by `rm -rf .next && npm run build` retry, not a real code problem.
