### Partnership Ads: flag the account's own posts as ineligible instead of "Ready to Launch" (PR #280)

The payoff from PR #278's richer error messages: the user's next real retry surfaced a precise, unambiguous Graph error instead of a generic one — `"Invalid parameter — Review 1 error — @sheshaayurveda isn't a partner of @sheshaayurveda. You can select a post, where @sheshaayurveda is a partner to turn into a partnership ad. — (code 100, subcode 3867018)"`. This is **not a bug in how this app builds the request** — it's a genuine Meta rule: a Partnership (branded-content) Ad requires the advertiser to be a tagged *partner* on someone *else's* post, which is structurally impossible for a post the business authored itself. The item that failed this way (`@sheshaayurveda`'s own reel) had been showing as "Launch Ready" in Explore Ads the entire time, because Content Discovery still reports `permission_status: AUTHORIZED` for the account's own posts — a separate, unrelated "can this be boosted as an ordinary ad at all" signal that this app's `permissionState()` was treating as equivalent to "eligible for a Partnership Ad specifically." They aren't the same thing, and nothing distinguished them anywhere in the UI until the user hit the real Graph error at actual launch time, every time, for this entire class of content.

Fixed by teaching `lib/partnershipContent.js` to recognize this case directly and cheaply: `isOwnPost(item, igUserId)` compares `item.author.ig_user_id` against the selected Instagram account (Content Discovery already returns this field — no extra API call needed), and `permissionState()` now returns a distinct `"own"` state, checked before `permission_status` is even consulted. Wired through everywhere Explore Ads branches on permission state: `PartnerCard` shows a 🚫 badge ("Your own post — can't become a Partnership Ad") in place of the hover "✓ Select" prompt; these items are excluded from both the ready-to-queue and needs-permission buckets in `ExploreTab.js` (so they no longer inflate "Add to Queue"'s count or get swept into a bulk permission request); `ExpandedCardModal` shows a plain explanatory sentence instead of an "Add to Queue"/"Request Permission" button that would have been nonsensical here (there's no permission to request); and a new "Not a Partner Post" option was added to the Eligibility filter dropdown so a user can see exactly which of their results fall into this bucket, and why, without having to guess from a launch failure.

Verified via mocked preview: a 2-item grid (one of the account's own posts, one genuine creator-tagged post) shows the correct badge and tooltip on the own post, selecting both together shows "Add to Queue (1)" — only the real creator post counts — and the new eligibility filter option renders correctly. `npm run lint && npm run build` clean. This closes out the specific content item (`@sheshaayurveda`'s own reel) that had been the subject of the last several rounds' debugging — it was never going to launch as a Partnership Ad by design, and now the app says so up front instead of letting it get queued.

### Partnership Ads: fix video content without ad_code always failing at creative creation (PR #278)

The user's next real re-attempt after PR #276 — this time via a curl capture of the actual launch request/response, which made this one far more diagnosable than prior rounds. Two video reels, both with `adCode: null` in the request body (one the brand's own post, one a creator-tagged post Content Discovery still didn't attach a code to), both failed at "Creating ad creative" with a bare `"Invalid parameter"` — no further detail at all.

Root cause: with no `ad_code`, the only path to a working creative is `source_instagram_media_id`, which per Meta's own branded-content flow requires a prior registration step (`registerVideoSource`, `POST /{ad_account_id}/advideos`) validating that specific Instagram video as a usable source for *this* ad account — skip it, and the later creative-creation call referencing that media id gets rejected. That registration step was gated by `item.mediaType === "VIDEO"`, an exact, case-sensitive match — and the real queued item's `mediaType` in the captured request was `"video"` (lowercase). The check silently evaluated false, the registration step never ran, and the only symptom was the generic, uninformative "Invalid parameter" several steps later — exactly the dead end reported. Fixed to compare case-insensitively (`String(item.mediaType).toUpperCase() === "VIDEO"`).

Two supporting fixes, both aimed at making the *next* dead-end faster to diagnose than this one was: `lib/facebookGraph.js`'s error extraction now folds in Graph's own `error_user_title`/`error_user_msg`/`code`/`error_subcode` when present, instead of only ever surfacing the often-generic top-level `message` — "Invalid parameter" alone gave nothing to act on, and this round only moved forward because the user supplied the full curl/response rather than relying on the dashboard's own error text. And `registerVideoSource`'s own outcome (success or failure) is now recorded as a visible, non-fatal "Video registration" step in the launch result instead of being silently discarded in an empty `catch {}` — so a real failure there is visible immediately instead of only ever showing up as a confusing downstream creative-creation error.

The user framed this as needing to "handle all cases, with content id, with partnership code and permalink as well" — confirmed via investigation that permalink-sourced and content-id-sourced items (anything without an `ad_code`) all funnel into the exact same `source_instagram_media_id` code path this fixes, so the fix applies uniformly across all three sourcing modes whenever the content is video; no per-mode special-casing was needed or added.

Verified with a standalone script: the case-insensitive check now matches a real lowercase `"video"` value (previously silently false) while leaving uppercase/mixed-case/non-video values unaffected; the error extractor folds in rich Graph error detail when present and falls back to the bare message when it isn't. A mocked-preview launch confirms the new "Video registration — <name>" step renders correctly alongside Creative/Ad in the result list. `npm run lint && npm run build` clean. **Not yet confirmed**: the user's own exact failing videos, re-launched — this needs a real retry now that the actual root cause (not just a guess) has been fixed.

### Partnership Ads: fix launch failing for a 2nd ad account on the same content (PR #276)

The user's next real test after PR #268 shipped: launch the identical queued content (via Partnership Code and separately via Explore Ads) from a *second* ad account on the same Instagram account/Business. It had worked from the first ad account; it failed from the second. The user's own framing was exactly right: "this should have nothing to do with ad account... this should only be used when we are launching ad" — eligibility/lookup is (and should be) scoped by Business+Instagram account, not ad account; only actual ad/creative creation is genuinely ad-account-specific. Investigation found two real, independent bugs that both fit that framing:

1. `pages/api/fb/partnership/launch.js` already does a fresh re-verification `lookupContent` call for every item right before using it (correctly scoped by `businessId`+`igUserId`, confirmed via investigation to have zero `accountId` dependency anywhere in the Content Discovery layer) — but it then threw away that fresh result and passed `item.adCode` (the value frozen into the queue at whatever moment the content was originally discovered, possibly hours or days earlier, from a different ad account's own session) into both `registerVideoSource` and `createBrandedCreative`. Meta's branded-content `ad_code` ("boost post access token") isn't confirmed to be an indefinitely-reusable, stable value — using a stale one can plausibly fail even though the content is still fully eligible. Fixed to use the re-verification lookup's own fresh `ad_code` (`firstPartnershipInfo(verified).ad_code`, the same `CONTENT_FIELDS` already requests it) instead, falling back to the queued value only if the fresh lookup somehow didn't return one.
2. `LaunchWizardModal`'s Facebook Pixel/UTM/Page settings are remembered per ad account (`getPartnershipSettings`/`setPartnershipSettings`, keyed by `accountId`) — by design, since a pixel genuinely is ad-account-specific. But the Facebook Page isn't: it should match whichever Page is linked to the Instagram account in use, not vary by ad account. The first time the wizard opens for a *different* ad account, there's no saved settings record yet, and it silently defaulted to `pages?.[0]?.id` — an arbitrary first entry in the *entire* list of every Page the token can see, with zero relationship to the Instagram account actually selected. A wrong default Page here makes `facebook_branded_content.sponsor_page_id` invalid for that specific launch, independent of the content or ad_code being perfectly fine. Fixed to default to the Page whose own `instagram_business_account.id` matches the selected Instagram account instead — correct regardless of which ad account is in use, still fully overridable from the dropdown.

Verified: a standalone script (server-side Graph-call logic, can't be exercised through the browser-mocked-preview convention) confirms the ad_code selection — fresh preferred over stale, falls back when the fresh lookup has none, unchanged when fresh and stale happen to match. A mocked-preview scenario with two Pages (the Instagram-linked one deliberately *not* first in the list) and no saved settings for the ad account confirms the wizard now defaults to the correctly-linked Page. `npm run lint && npm run build` clean. **Not yet confirmed**: the user's own exact failing scenario — the same content launched from the second ad account — needs a real re-attempt now that both fixes are live.

### App-wide: fix Ad Accounts list failing entirely for Business-Manager-owned accounts (PR #274)

Immediate payoff from PR #272's error surfacing: the account owner opened Raw Data as the affected user and got a precise answer instead of a guess — `(#100) Requires business_management permission to access the field`, with zero ad accounts shown. This is a *narrower and more specific* bug than the Advanced-Access/Tester theory flagged in §7 after PR #272 — not every `pages_show_list`/`ads_read`-style scope gate, but one exact field: `/me/adaccounts`'s request for `business{id,name}` (the owning Business Manager, fetched for Partnership Ads' Content Discovery API) requires the `business_management` permission specifically, which this app has never requested in its OAuth `scope` string. Graph doesn't null out just that one field when the permission is missing — it fails the **entire** ad accounts list. ### Copy Ads: copy ads concurrently instead of one at a time (PR #221)

At the user's request, after noticing copying several ads took noticeably longer than expected: the copy step (`pages/api/fb/copy-ads/copy.js`) processed every selected ad fully sequentially in a `for` loop — each ad is several Graph calls on its own (re-fetch, asset copy, possible video processing poll, creative create, ad create), so an N-ad batch took roughly N× one ad's own latency.

Now runs up to `COPY_CONCURRENCY = 3` ads at once via `mapWithConcurrency`, a worker-pool runner that already existed in this codebase (`lib/metaInterestSearch.js`, used by `pages/api/fb/interest-recommendations.js` for its own bulk Graph calls) — reused rather than duplicated, no new dependency added. The cap is deliberately modest (not unbounded) since this route already issues several *write* calls per item and an uncapped burst risks tripping Meta's own per-app/per-user rate limiting.

The one real correctness risk introduced by concurrency: several selected ads commonly share one base creative's image/video asset, and the existing de-dupe (`hashMap`/`videoIdMap`, "copy only if not already copied") was a plain `Map` checked-then-set per ad — safe when strictly sequential, but a race once ads run concurrently, since two ads could both see a miss before either finishes copying, double-copying the same asset. Fixed with a new `createAssetCopyCoordinator` (`lib/adCopy.js`) that caches the **in-flight promise** keyed by source hash/video id instead of just the eventual value — every concurrent caller for the same asset awaits the one real copy; the check-then-set itself is still safe without a lock because it's fully synchronous (no `await` between the `has` check and the `set`).

Each ad now writes its result into its own array index (via `mapWithConcurrency`'s per-item return, flattened afterward) instead of pushing into a shared array in completion order — so the result screen still lists ads in the user's original selection order regardless of which ad actually finishes copying first.

**Verification**: `npm run lint && npm run build` clean. Pure server-side concurrency/Graph-call change with no new client-facing contract, so the mocked-preview-harness convention wouldn't add anything here. Instead, the actual risk (the de-dupe race) was verified with a standalone scratch script replicating the exact `mapWithConcurrency` + `createAssetCopyCoordinator` pattern against fake async "Graph calls" with randomized delays — confirmed under Node's real event loop that results preserve original order, each shared asset is copied exactly once, every ad gets the correctly-mapped destination hash, and the concurrency cap is respected. **Not verified**: actual wall-clock speedup and real Graph rate-limit behavior against a live account — see §7.

**PR #210, correcting PR #206's own fix:** the "reduce the amount of data" error came back as `FUNCTION_INVOCATION_TIMEOUT` instead, on a busier account, even at the narrowed 7-day default. Root cause: `time_range`/`date_preset` on `GET /{accountId}/ads` **do not filter which ad rows come back at all** — they only scope nested insights-shaped sub-fields requested in the same call, a genuine gotcha this project's own earlier research (confirmed against Meta's reference docs) missed, since the docs page lists the param with no such caveat. **PR #212, same real-account session, one step further — the picker worked, the actual copy step didn't:** PR #210's `/insights`-based rewrite worked well enough that the user got all the way to submitting a real copy, which is itself implicit confirmation that fix landed correctly. The copy step's own ad re-fetch then threw `(#12) Old Instagram ID is deprecated for versions v22.0 and higher` on a real ad ("15th August | Women Video"). Root cause: `COPY_AD_FIELDS` requested `object_story_spec.instagram_actor_id`, which Meta deprecated in Graph API v22.0 in favor of `instagram_user_id` (this app runs v23.0) — querying the old field name throws outright, and a single-object `GET` (what the copy step's re-fetch uses, unlike the listing step's `?ids=` batch) fails its *entire* call over one bad field. Renamed the field; also added `fetchAdForCopy()`'s fallback for the case the error's own wording ("**Old** Instagram ID," not "unsupported field") implies — some ads may carry a genuinely never-migrated legacy-format id that fails even under the new field name — which retries once without the Instagram field at all and proceeds, flagging the created ad with a new non-blocking amber ⚠ warning step (distinct from both success and failure) rather than failing outright or silently dropping the Instagram association. Also added a defensive filter in the listing step to drop any `?ids=` batch entry missing its own `id`, since that endpoint appears to isolate a per-object field error rather than failing the whole batch — plausibly why this exact ad showed up fine in the picker but failed on the copy step's own re-fetch.

**PR #214, immediately after — the IG-id rename itself broke the picker for every account:** right after PR #212 shipped, the source ads picker started showing "No ads found" for every account tried. `instagram_user_id` turned out to be the correct field (Meta's own `object_story_spec` reference lists it with no deprecation notice, and the old field's own error message literally says to switch to it) — the rename wasn't wrong. The real bug: the listing step's `?ids=`-batch-of-50 fetch requests this same field with no fallback, unlike the per-ad re-fetch PR #212 just fixed. If that field fails on a batch for any reason, the whole batch throws, and the old code silently swallowed every failed batch (`Promise.allSettled` + bare `continue`) — turning "every batch is failing" into an indistinguishable "No ads found" instead of a visible error. Fixed by giving the listing batch the same old-Instagram-id fallback `fetchAdForCopy` already had, and — just as importantly — making `fetchCopyableAds` throw a real error if every batch still fails after that, instead of silently returning `[]`. Honesty note in the PR itself: this targets the most likely cause given the timing, but the actual Graph error text was never seen from here (`graphGet` logs every call, success or failure, to `/logs` — the next thing to check if "No ads found" ever shows up again with no visible error, since that would point at the `/insights` discovery step itself instead).

Create a throwaway page like `pages/explore-<name>-preview.js` that:
```jsx

import { AccountProvider } from "@/components/AccountProvider";

  window.__xPreviewMocked = true;
  const realFetch = window.fetch.bind(window);
  window.fetch = (url, opts) => {
    // intercept /api/fb/data, /api/fb/custom-conversions, /api/fb/explore-insights
    // with hand-built fake JSON responses, fall back to realFetch otherwise
  };
}

export default function Preview() {
```

Run it via a `npm run dev` on a throwaway port (e.g. `PORT=3101 npm run dev` inside the worktree, backgrounded) and open it in the Browser tool with `preview_start({ url: "http://localhost:3101/explore-<name>-preview" })`. **Delete the preview file before committing** — it must never ship.

**Caveat:** localStorage (views, cached query results) persists across different preview pages on the same origin (`localhost:<port>`) — a stale cached result can carry over between test runs. Use the app's own "Hard Refresh" button (bypasses the cache lookup) rather than "Update This View" when you need to guarantee a fresh fetch against your mock.

**Caveat:** a fresh `npm install && npm run build` in a brand-new worktree has occasionally failed once with a `next/font/google` module-not-found error — a known transient issue, fixed by `rm -rf .next && npm run build` retry, not a real code problem.
