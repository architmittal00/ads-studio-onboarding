### Copy Ads: copy ads concurrently instead of one at a time (PR #221)

At the user's request, after noticing copying several ads took noticeably longer than expected: the copy step (`pages/api/fb/copy-ads/copy.js`) processed every selected ad fully sequentially in a `for` loop — each ad is several Graph calls on its own (re-fetch, asset copy, possible video processing poll, creative create, ad create), so an N-ad batch took roughly N× one ad's own latency.

Now runs up to `COPY_CONCURRENCY = 3` ads at once via `mapWithConcurrency`, a worker-pool runner that already existed in this codebase (`lib/metaInterestSearch.js`, used by `pages/api/fb/interest-recommendations.js` for its own bulk Graph calls) — reused rather than duplicated, no new dependency added. The cap is deliberately modest (not unbounded) since this route already issues several *write* calls per item and an uncapped burst risks tripping Meta's own per-app/per-user rate limiting.

The one real correctness risk introduced by concurrency: several selected ads commonly share one base creative's image/video asset, and the existing de-dupe (`hashMap`/`videoIdMap`, "copy only if not already copied") was a plain `Map` checked-then-set per ad — safe when strictly sequential, but a race once ads run concurrently, since two ads could both see a miss before either finishes copying, double-copying the same asset. Fixed with a new `createAssetCopyCoordinator` (`lib/adCopy.js`) that caches the **in-flight promise** keyed by source hash/video id instead of just the eventual value — every concurrent caller for the same asset awaits the one real copy; the check-then-set itself is still safe without a lock because it's fully synchronous (no `await` between the `has` check and the `set`).

Each ad now writes its result into its own array index (via `mapWithConcurrency`'s per-item return, flattened afterward) instead of pushing into a shared array in completion order — so the result screen still lists ads in the user's original selection order regardless of which ad actually finishes copying first.

**Verification**: `npm run lint && npm run build` clean. Pure server-side concurrency/Graph-call change with no new client-facing contract, so the mocked-preview-harness convention wouldn't add anything here. Instead, the actual risk (the de-dupe race) was verified with a standalone scratch script replicating the exact `mapWithConcurrency` + `createAssetCopyCoordinator` pattern against fake async "Graph calls" with randomized delays — confirmed under Node's real event loop that results preserve original order, each shared asset is copied exactly once, every ad gets the correctly-mapped destination hash, and the concurrency cap is respected. **Not verified**: actual wall-clock speedup and real Graph rate-limit behavior against a live account — see §7.

### Copy Ads: real cross-account copy confirmed, but text came through blank — fixed (PR #219)

**First confirmed end-to-end success for this feature**: the user reported a real image ad copied from one ad account into another, creative and all — the first time anything in this app has built a creative from raw assets across accounts and actually worked. But Primary Text, Headline, and Description all came through blank on the copied ad, even though the image/page copied fine.

Root cause: the source ad was built with Meta's **Multiple Text Options** (Advantage+ creative text enhancements — on by default in Ads Manager's own ad composer). Ads built this way store their actual copy in `creative.asset_feed_spec.bodies/titles/descriptions`, not in `object_story_spec.link_data.message/name/description` — those often come back empty for such ads, since Meta renders the live ad from the asset feed rather than the story spec's own text fields. `lib/adCopy.js` already fetched a sliver of `asset_feed_spec` (just `bodies`, added only for `classifyAd`'s Dynamic-Creative-only check) but discarded it entirely when building the new creative — so the image/page/link copied correctly while the text silently dropped.

Fixed by fetching the full `asset_feed_spec` (bodies, titles, descriptions, link_urls, call_to_action_types, images, videos, ad_formats, optimization_type), remapping any `image_hash`/`video_id` it references through the same hash/video maps already used for `object_story_spec` (new `rebuildAssetFeedSpec`), and sending it alongside `object_story_spec` on creative creation whenever it has real content (new `hasAssetFeedContent`) — Meta's `adcreatives` endpoint accepts both together, the same way Ads Manager itself builds these ads. `collectImageHashes`/`collectVideoIds` now take the whole `creative` object instead of just `object_story_spec`, so assets referenced only from the asset feed get copied too.

**Not yet re-confirmed against a real account** — same structural limitation as every other server-side Graph-call fix in this feature's history: there's no way to exercise a real `adcreatives` mutation from this environment. `npm run lint && npm run build` clean; diff scoped to `lib/adCopy.js` + `pages/api/fb/copy-ads/copy.js` only.

### Copy Ads — clone ads across ad accounts into an existing ad set (PR #204, #206, #208, #210, #212, #214, #217)

New tab for a common D2C-agency pattern: the same Page running ads out of several ad accounts. Pick ads already running in one ad account, pick a destination ad account + an **already-existing** ad set in it, and the ad's creative (plus a new Ad pointing at it) gets rebuilt there. Deliberately scoped as a creative+ad clone, not a campaign/targeting migrator — the destination ad set's own budget/targeting are never touched, which sidesteps the much harder problem of mapping custom audiences/pixels/geo-targeting across accounts. Page and Instagram actor carry over completely unchanged (the feature's own premise is that the Page is identical across both accounts).

This is the first place in the app that builds a standard `object_story_spec` creative from raw assets instead of reusing an existing `creative_id` by reference — every prior "duplicate an ad" path (`pages/api/fb/duplicate-ad.js`, the Launch tab's own duplicate flow) explicitly avoids re-deriving a creative's full spec, since a creative is a standalone Graph object normally just referenced by id. That shortcut doesn't work across ad accounts (a `creative_id` can't be referenced from a different account), so this had to actually rebuild one. New `lib/adCopy.js`: images copy via Meta's own cross-account `copy_from` mechanism on `/adimages` (confirmed via Meta's reference docs — the account making the call just needs read access to the source account's creatives, which the user's own token already has); video has no `copy_from` equivalent, so it's re-ingested via `file_url` pointed at the source video's own `source` download URL, with a short bounded poll for Meta's async processing before the creative references it. Catalog/DPA ads (`product_set_id`) and Dynamic Creative ads (`asset_feed_spec` only) are detected up front (`classifyAd`) and shown disabled with a reason in the ad picker, rather than selectable and only failing later. Image/video assets are de-duplicated across an entire copy batch, not re-copied per ad, when several selected ads share the same creative asset. Same two-phase safety pattern as every other launch flow in this app: every created ad is `PAUSED` first, only flipped to `ACTIVE` in one final step and only if the whole batch succeeded.

**Real bug caught and fixed during mocked-preview verification** (same class as Partnership Ads' `BulkPermissionModal` bug one round earlier): the result screen briefly showed "1 of 0 ads created" instead of "1 of 2" — `CopyAdsModal` read `ads.length` live off a prop that the parent page shrinks (clearing the selection) the moment a copy succeeds. Fixed by snapshotting the selected ads once at mount via `useState(adsProp)` instead of reading the live prop throughout the component's life.

**PR #210, correcting PR #206's own fix:** the "reduce the amount of data" error came back as `FUNCTION_INVOCATION_TIMEOUT` instead, on a busier account, even at the narrowed 7-day default. Root cause: `time_range`/`date_preset` on `GET /{accountId}/ads` **do not filter which ad rows come back at all** — they only scope nested insights-shaped sub-fields requested in the same call, a genuine gotcha this project's own earlier research (confirmed against Meta's reference docs) missed, since the docs page lists the param with no such caveat. **PR #212, same real-account session, one step further — the picker worked, the actual copy step didn't:** PR #210's `/insights`-based rewrite worked well enough that the user got all the way to submitting a real copy, which is itself implicit confirmation that fix landed correctly. The copy step's own ad re-fetch then threw `(#12) Old Instagram ID is deprecated for versions v22.0 and higher` on a real ad ("15th August | Women Video"). Root cause: `COPY_AD_FIELDS` requested `object_story_spec.instagram_actor_id`, which Meta deprecated in Graph API v22.0 in favor of `instagram_user_id` (this app runs v23.0) — querying the old field name throws outright, and a single-object `GET` (what the copy step's re-fetch uses, unlike the listing step's `?ids=` batch) fails its *entire* call over one bad field. Renamed the field; also added `fetchAdForCopy()`'s fallback for the case the error's own wording ("**Old** Instagram ID," not "unsupported field") implies — some ads may carry a genuinely never-migrated legacy-format id that fails even under the new field name — which retries once without the Instagram field at all and proceeds, flagging the created ad with a new non-blocking amber ⚠ warning step (distinct from both success and failure) rather than failing outright or silently dropping the Instagram association. Also added a defensive filter in the listing step to drop any `?ids=` batch entry missing its own `id`, since that endpoint appears to isolate a per-object field error rather than failing the whole batch — plausibly why this exact ad showed up fine in the picker but failed on the copy step's own re-fetch.

**PR #214, immediately after — the IG-id rename itself broke the picker for every account:** right after PR #212 shipped, the source ads picker started showing "No ads found" for every account tried. `instagram_user_id` turned out to be the correct field (Meta's own `object_story_spec` reference lists it with no deprecation notice, and the old field's own error message literally says to switch to it) — the rename wasn't wrong. The real bug: the listing step's `?ids=`-batch-of-50 fetch requests this same field with no fallback, unlike the per-ad re-fetch PR #212 just fixed. If that field fails on a batch for any reason, the whole batch throws, and the old code silently swallowed every failed batch (`Promise.allSettled` + bare `continue`) — turning "every batch is failing" into an indistinguishable "No ads found" instead of a visible error. Fixed by giving the listing batch the same old-Instagram-id fallback `fetchAdForCopy` already had, and — just as importantly — making `fetchCopyableAds` throw a real error if every batch still fails after that, instead of silently returning `[]`. Honesty note in the PR itself: this targets the most likely cause given the timing, but the actual Graph error text was never seen from here (`graphGet` logs every call, success or failure, to `/logs` — the next thing to check if "No ads found" ever shows up again with no visible error, since that would point at the `/insights` discovery step itself instead).

### The mocked-preview-harness convention (use this for any Explore UI verification)

Create a throwaway page like `pages/explore-<name>-preview.js` that:
```jsx
import { SessionProvider } from "next-auth/react";
import { AccountProvider } from "@/components/AccountProvider";
import Explore from "./explore"; // or whatever real page you're testing

const FAKE_SESSION = { user: { name: "Test User" }, expires: "2099-01-01T00:00:00.000Z" };

  window.__xPreviewMocked = true;
  const realFetch = window.fetch.bind(window);
  window.fetch = (url, opts) => {
    // intercept /api/fb/data, /api/fb/custom-conversions, /api/fb/explore-insights
    // with hand-built fake JSON responses, fall back to realFetch otherwise
  };
}

export default function Preview() {
  return (

      <AccountProvider><Explore /></AccountProvider>
```

Run it via a `npm run dev` on a throwaway port (e.g. `PORT=3101 npm run dev` inside the worktree, backgrounded) and open it in the Browser tool with `preview_start({ url: "http://localhost:3101/explore-<name>-preview" })`. **Delete the preview file before committing** — it must never ship.

**Caveat:** localStorage (views, cached query results) persists across different preview pages on the same origin (`localhost:<port>`) — a stale cached result can carry over between test runs. Use the app's own "Hard Refresh" button (bypasses the cache lookup) rather than "Update This View" when you need to guarantee a fresh fetch against your mock.

**Caveat:** a fresh `npm install && npm run build` in a brand-new worktree has occasionally failed once with a `next/font/google` module-not-found error — a known transient issue, fixed by `rm -rf .next && npm run build` retry, not a real code problem.
