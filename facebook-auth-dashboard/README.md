# Facebook Auth Dashboard

A minimal Next.js (Pages Router) dashboard that lets a user log in with Facebook and view their profile, Facebook Pages, and Ad Accounts via the Graph API.

## How it works

- Auth is handled by [NextAuth.js](https://next-auth.js.org/) using the Facebook provider (`pages/api/auth/[...nextauth].js`).
- Login requests `public_profile,email,pages_show_list,pages_read_engagement,ads_read,ads_management` scopes. Note: **Page Public Content Access is not an OAuth scope** — it's a Facebook app *Feature*, granted via App Review in the Meta App Dashboard (Settings → App Review → Permissions and Features), not something that can be requested through the login `scope` string.
- The Facebook access token is kept server-side in the session JWT, never exposed to the browser.
- Every authenticated page shares a persistent left sidebar (`components/Layout.js` + `components/Sidebar.js`) for navigation and sign-out, replacing the old per-page top nav bar. It's an icon-rail sidebar, matching the slim collapsible pattern used across the team's other internal tools: icon-only by default (68px), with a panel-toggle button to expand it to icon+label (220px) — the choice is a per-device preference (`localStorage`, via `getSidebarCollapsed()`/`setSidebarCollapsed()` in `lib/clientStorage.js`), not re-asked every visit. The footer shows the signed-in user's Facebook avatar (or initials if no profile photo) plus a sign-out icon button.
- After login, the user lands on `/report` — the **Account Handover Report**: a wide dashboard with a sticky section nav (scroll-spy), sortable scroll-capped and searchable tables (every column header is clickable to sort; long names wrap up to 3 lines and only then ellipsize, with a hover tooltip for the full text), and creative thumbnails wherever an individual ad is shown — click one to open it fullscreen; video ads actually play (direct video `source` URL resolved server-side from the creative's `video_id`), not just a static thumbnail.
  - **Date range**: a selector (Today / Last 7 Days / Last 30 Days / Custom) at the top drives the entire report — overview, top campaigns, pareto, structure, budget/creative recommendations all recompute for whatever's selected. Custom uses two date inputs plus an Apply button (so it doesn't refetch on every keystroke). Best Week/Best Month stay on their own fixed 90-day/6-month lookback regardless, since they're about historical context rather than "the current view" — noted inline so that's not confusing. A gear button next to the selector opens **Default Landing Range** — Today/Last 7 Days/Last 30 Days, saved per-device (`localStorage`, like the last-viewed account) — which range the report opens to on every visit, independent of whatever range is selected mid-session.
  - **Metric drill-down**: click any Overview stat (Spend, Purchases, ROAS, CTR, CVR) to open a trend chart — daily breakdown for ranges up to a month, weekly beyond that — rendered with a small dependency-free SVG line chart (`components/TrendChart.js`), no charting library added.
  - Covers spend/purchases/ROAS/CTR/CVR for the selected range, top spending campaigns with % of total revenue (click a row to jump into the structure drill-down), the ads driving 80% of purchase revenue with % of revenue per ad, pixel health, and high-frequency ads outside retargeting — ad-level tables show each ad's status (Active/Paused/etc.) alongside its thumbnail.
  - Four more "where does 80% of purchase revenue come from" breakdowns, same pattern as the creative-level one: **by age & gender** (via `breakdowns=age,gender`), a full **by creative type** split (Static/Video/Catalog, derived from each ad's creative — a catalog ad is detected via `product_set_id`, not a Facebook breakdown dimension — shown in full rather than cut at 80%, since there are only ever 3 possible groups), **by platform & placement** (e.g. "Instagram · Reels", "Facebook · Feed" — one combined breakdown via `breakdowns=publisher_platform,platform_position`, not split into a separate platform-only table), and **by product** — Facebook has no native per-product revenue breakdown outside catalog/DPA reporting, so this is reverse-engineered from each ad's landing page URL (a Shopify-style `/products/<handle>` path becomes the product name; anything else falls back to the raw path), resolved from the ad's own creative — including its top-level `call_to_action` field, not just the one nested under `object_story_spec.video_data`, which turned out to be where most video/Reels ads (built by boosting an existing Page post, with no `object_story_spec` of their own) actually carry their link — or, failing that, from the underlying Page post's own `link`/`call_to_action`/`attachments` fields as a last resort. Catalog/Dynamic-creative ads have no single fixed URL — Facebook generates the real destination per product at serve time — so their revenue is called out as its own "Catalog / Dynamic creative" row; ads where neither lookup finds a URL fall into "Unknown landing page" instead of being silently dropped, shown only once it's more than 10% of spend (`LANDING_PAGE_SPEND_CUTOFF_PCT` in `pages/api/fb/report.js` — also used for the "Could not resolve a landing page for N ad(s) linked via an existing Page post" warning banner, which only appears once those unresolved ads cross the same 10% threshold, instead of firing for any account with a handful of permission-gated Pages) since below that it's rarely worth the clutter — decided by its own share of spend, not by where it'd normally rank in the 80%-of-revenue cutoff (which would hide it whenever it has little attributable revenue, exactly the "spend with nothing to show for it" case most worth flagging), so this explicitly overrides that cutoff in both directions rather than just filtering its result. Past the threshold, the row expands into a table of the specific highest-spend ads behind it (ad ID, name, campaign, a direct Ads Manager link) so it's debuggable rather than just a number. Each breakdown shows spend, revenue, % of revenue, ROAS, and purchases per group.
  - **By State** is a *spend* pareto instead — Facebook doesn't return purchase revenue broken down by region for any account tested (see the caveat below), so this shows the top states by spend concentration rather than reusing the broken revenue framing.
  - **Account Structure** is a single Ads-Manager-style indented tree table (campaign → ad set → ad) with a search box (matches at any level; a match on an ancestor shows everything beneath it, a match on a descendant only shows that branch, auto-expanded), Expand All/Collapse All, a sort-by-metric control (Name/Spend/Purchases/ROAS, applied within each level so the hierarchy stays intact), status dots at every level including individual ads, and consistent Spend/Purchases/ROAS/Creatives columns (dashed where not applicable).
  - **Budget Utilization & Creative Count** is one merged, CBO/ABO-aware section with a tab switch (CBO Campaigns / ABO Ad Sets, not stacked) — CBO campaigns judged at the campaign level, ABO campaigns judged ad set by ad set (where the budget actually lives). Rows spending under 100% of their own daily budget are highlighted (amber left-edge row). The creative recommendation is budget-driven, not benchmarked against an account-wide average: for an underutilized row, its current avg daily spend (7d) is divided by its live creative count to get an **Avg Spend/Creative**, then `ceil(dailyBudget / avgSpendPerCreative)` gives the **Recommended** creative count needed to spend the full budget at that same rate — **Additional Needed** is the gap versus what it already has (e.g. a ₹10k-budget ad set spending ₹6k/day across 2 creatives → ₹3k/creative → needs 4 total → +2). Fully (or over-) utilized rows show no recommendation ("—") since there's no unspent budget left for extra creatives to unlock.
- `/strategy` ("Figure Out Strategy") recommends a campaign/ad-set structure from the agency's 8-strategy playbook (`lib/strategyEngine.js`), based on three inputs: daily budget (for displaying real currency amounts per campaign — doesn't affect which strategy is picked), whether the owner is open to experimenting with a full TOF/MOF/BOF funnel vs. wanting Bottom-of-Funnel only, and account history — pick one of the connected ad accounts, or mark it fresh/new with no prior data. **This account selector only decides the recommendation signal, not where a strategy launches to** — marking it fresh (no history to compute a signal from) used to also disable Launch entirely app-wide, which meant Strategies 2/4/6 (built specifically for fresh accounts) were never actually launchable. Now, picking "fresh" reveals a second, required "Launch to which account?" picker (any real connected account) — the two are independent, so a fresh signal and a real launch target can coexist. For a connected account picked directly (not via the fresh path), "has history" isn't declared by the user — it's calculated (`/api/fb/strategy-signal.js`): fetch the account's trailing 30 days (impressions, spend, `cpm`, `link_click`/purchase actions), simulate spending the entered daily budget entirely on Top-of-Funnel traffic for a month at half the account's blended CPM (TOF/reach placements typically buy cheaper), convert that to a projected visitor count using the account's own impression→link-click ratio, and compare against the actual link clicks it already got in the last 30 days — if prospecting at full budget couldn't even match what the account already generates organically, its existing pool is judged large enough to build a strategy around. Needs both link clicks and purchases present in the window to run at all (otherwise treated as not-enough-history, with no fallback guessing); needs a daily budget entered to run the projection, so recommendations wait on that now rather than treating budget as purely cosmetic. When more than one strategy matches (several pairs share identical stated conditions, differing only in how aggressive the prospecting split is), all matches are shown ranked — "Recommended" first, "Also consider" after — rather than the tool silently picking one. For "not open to experiment," the playbook's conditions aren't a clean single axis (3/4 are conditioned on history, 7/8 on "no specific idea in mind," a dimension this tool doesn't ask about separately) — resolved by folding "no specific idea" into the existing history answer rather than adding a third question: a history-backed account ranks Strategy 3 above 7/8, a fresh account ranks Strategy 4 above 7/8 (3 is excluded outright — it hard-requires a pool that doesn't exist yet). Each recommended strategy shows a plain-language rationale for why it fits (`rationale` on each entry in `lib/strategyEngine.js`); per-campaign budget amounts round to the nearest 100 when the total daily budget is under 10,000, or the nearest 500 at or above that (`roundBudgetAmount()`), so recommendations read as "₹16,000/day" rather than "₹15,970.42/day". A "See the other N strategies" toggle reveals every non-matching strategy too, each with a plain-language reason it wasn't picked (`explainMismatch()`) instead of just disappearing.
  - **Launching a strategy** (`components/LaunchPanel.js`, `pages/api/fb/launch-strategy.js`) creates the real campaign(s) and ad set(s) on the live ad account — this is the one place in the app that writes to Facebook rather than just reading. Everything is created **paused first**, regardless of the chosen final status, and only flipped to Active in a last step if every object above it succeeded; nothing created is ever auto-deleted on a partial failure, and the panel reports exactly which campaign/ad set/audience succeeded or failed with Facebook's own error message. Every created campaign/ad set name currently starts with a `TEST-` prefix (`TEST_PREFIX` in `lib/campaignLaunch.js`) while this flow is still being verified against real accounts, so nothing it creates can be mistaken for a real production campaign in Ads Manager — drop the prefix once the flow is trusted. Targets India and a 1% lookalike ratio — not configurable yet. Facebook Page is picked per launch; the **pixel is asked for once per ad account and remembered** after that (`getPixelMapping()`/`setPixelMapping()` in `lib/clientStorage.js`, same per-device `localStorage` pattern as everything else there), changeable anytime. Retargeting ad sets (BOF in Strategies 1/3/5, and MOF in every strategy that has an MOF campaign — 1/2/5/6) target **both** website visitors and Page/ad engagers, unioned as two separate `custom_audiences` entries rather than one combined audience, since they're different Meta audience objects under the hood (a `WEBSITE` pixel audience vs. a Page-engagement one). MOF uses this regardless of account history — it retargets the pool its own TOF campaign builds up over time, not a pre-existing one, which is why it isn't gated behind the history check the way BOF's retargeting ad set is. These, plus the Lookalike-of-buyers audience, are all found-or-created — `lib/audienceManager.js` looks for ones this tool already made (tagged `AUTO-Visitors180d`, `AUTO-Engagers365d`, `AUTO-Purchasers730d-Seed`, `AUTO-Purchasers-LAL1pct-IN`) before creating new ones, so repeat launches don't duplicate them. Strategy 7's "Hero"/"Grooming" ad sets are deliberately simplified for now — no catalog/product-set targeting yet, flagged as a future enhancement rather than attempted half-right.
    - **Strategy 8's interest targeting** (`components/InterestPicker.js`, `components/InterestTargetingSection.js`, `lib/metaInterestSearch.js`) used to hardcode all 3 ad sets to the same literal `"Beauty"` placeholder. Each ad set now gets its own live, Meta-search-backed, **multi-select** picker — type a term and see real interests with real audience sizes, "exactly like search on Meta" (`/api/fb/interest-search.js`, a thin wrapper over `GET /search?type=adinterest`); an ad set can target more than one interest (Meta ORs them together within one `flexible_spec` entry — reach anyone matching *any* of them — see `buildAdsetPayload()` in `lib/campaignLaunch.js`), each shown as a removable chip with its own audience-size range. **The picker lives directly on the Strategy 8 recommendation card on `/strategy`** (`pages/strategy.js` owns the chosen interests, keyed by strategy id) — not inside the Launch pop-up — so searching, reviewing AI suggestions, and choosing interests all happen before Launch is ever clicked; `components/LaunchPanel.js` just reads the choices back as a plain, read-only summary ("Ad set 1: Skin care + Hair care") and disables Launch until every ad set has at least one. AI recommendations (`/api/fb/interest-recommendations.js`) load **automatically in the background** — no button to click — the moment there's something to analyze: the account's top landing pages by revenue over a fixed last-30-days window (`/api/fb/top-landing-pages.js`, independent of whatever range is selected elsewhere) get sent to Gemini via [OpenRouter](https://openrouter.ai) (`lib/openrouter.js`) for 50+ candidate interest/category names, each resolved against Meta's real targeting system and deduped into a ranked list (consensus count — how many AI suggestions led to the same real interest — then audience size) via a small hand-rolled concurrency limiter (`mapWithConcurrency()`, since `/search?type=adinterest` takes one query per call with no batch variant). The top 3 ranks pre-fill ad sets 1/2/3 as a starting point, but **every** matched suggestion (up to `MAX_DISPLAYED_INTERESTS`, 50) is shown inline under each picker as a click-to-add "Suggested" list — not hidden behind typing into the search box — so the user can browse and add from the full set, not just whatever got auto-picked. For an account with fewer than 3 usable landing pages (including one explicitly marked "fresh" on the Strategy page), a **brand URL** input replaces the landing-pages step and the same AI call fires automatically once the user pauses on something that parses as a real URL — `lib/fetchPageText.js` fetches and strips the page server-side (a plain chat/completions call can't browse the web itself) and that extracted text goes into the same prompt instead. `interestChoices` (now an array of arrays — one list of `{id, name}` per ad set) is a hard requirement for launching any strategy with interest ad sets — `/api/fb/launch-strategy.js` returns a 400 rather than silently resolving something unintended if any ad set is left empty.
    - `pages/api/fb/launch-strategy.js` streams newline-delimited JSON rather than waiting for one final response — a progress line before each slow step (`"Creating campaign 2 of 3…"`, `"Creating ad set 1 of 3 for Campaign 3…"`) lets the panel show a live "what's happening right now" status with a spinner, instead of a plain "Launching…" button for however long the whole sequence takes.
    - Every created campaign/ad set name and audience result in the success view is **click-to-copy** — clicking it copies `name (id)` to the clipboard and flashes "Copied!" briefly as confirmation.
    - Audience steps distinguish **found existing** from **created** in the result badge (`step.created` from the API, not inferred from whether an `id` is present) — the badge used to say "Created" either way, which made "reused an existing audience" look like a fresh duplicate had been made. To verify an audience wasn't duplicated: open Ads Manager → Audiences and search the tagged name (e.g. `AUTO-Visitors180d`) — there should be exactly one with that name no matter how many times a strategy using it has been launched.
  - This landed in the middle of a live Meta API migration: the old `smart_promotion_type` flag for creating Advantage+ Shopping Campaigns was phased out (blocked for new campaigns from Marketing API v24.0, fully removed in v25.0), replaced by a **unified automation-lever model** — a campaign/ad set reads as "Advantage+" by *how it's configured* (CBO budget + a qualifying `bid_strategy` for budget automation, `targeting_automation: {advantage_audience: 1}` with only `geo_locations` alongside it for audience automation, no manual placement fields for placement automation) rather than an explicit flag. `GRAPH_API_VERSION` in `lib/facebookGraph.js` was bumped from `v21.0` to `v23.0` to get these fields — the minimum version that carries them. **This changes every existing Graph call the app makes, not just the new ones** — needs a full manual regression pass across `/report`, `/dashboard`, `/strategy`'s history check, and `/logs` after deploy. Also worth flagging: literal Advantage+ behavior is inherently a *Sales*-objective concept, so Top-of-Funnel ("optimized for site visits") is built as a plain `OUTCOME_TRAFFIC` campaign regardless of the strategy copy's "ASC (CBO)" label on that row — there's no Sales-objective equivalent for pure traffic. Its ad set optimizes for `LANDING_PAGE_VIEWS`, not `LINK_CLICKS` — LPV only counts a click that actually finishes loading the page (pixel-confirmed), buying real site visits rather than clicks that bounce before the page loads — which is also why its `promoted_object` carries `pixel_id` rather than `page_id`.
  - The Custom Audience creation rule shape (`lib/audienceManager.js`'s `websiteRule()`) and the Advantage+ audience-automation fields were implemented from Meta's current documentation and several 2026 sources on the API migration, and `subtype` on `/act_x/customaudiences` turned out to need two live round-trips to get right. First: a `rule`-based (pixel) request with `subtype: WEBSITE` came back `"The parameter 'subtype' is not supported in the current API version"` (error 2654/1870053) — removing `subtype` from that call fixed it. Then the LOOKALIKE call (`origin_audience_id` + `lookalike_spec`, no `rule`), built on the assumption that the same "subtype is inferred now" pattern applied everywhere, hit the opposite error: `"(#100) Missing parameter(s): subtype"`. So the real rule isn't "subtype is deprecated" — it's narrower: a `rule`-based request already implies WEBSITE on its own and rejects an explicit subtype as redundant, while a lookalike request still needs `subtype: LOOKALIKE` spelled out. Both calls now match what's actually been confirmed live rather than an extrapolated pattern; further surprises from this corner of the API are still plausible and will again surface as a direct Facebook error in the launch panel/`/logs` rather than silently creating something broken.
  - On success, the launch panel shows each created campaign as its own card with a **direct Ads Manager link**, its ad set(s) nested underneath with their own links (`components/LaunchPanel.js`'s `LaunchResult`) — not just a flat list of IDs.
- `/dashboard` ("Raw Data") shows the raw profile/Pages/Ad Accounts payload plus a manual per-account 30-day ROAS check.
- `/logs` shows the most recent Graph API calls (method, path, status, duration, full request/response) for debugging — see "API logging" below.
- `pages/api/fb/data.js` calls the Graph API (`/me`, `/me/accounts`, `/me/adaccounts`) for the account picker.
- `pages/api/fb/report.js` builds the handover report from several Graph API insights/campaign/pixel calls.
- `lib/facebookGraph.js` is a shared `graphGet()`/`graphPost()`/`graphGetAllPages()` helper all routes use — it logs every Graph API call, read or write (see below), and `graphGetAllPages()`/`graphGetInsights()` both paginate to completion rather than returning just the first page (see "Known Graph API caveats").

## API logging

Every Graph API call made by the server goes through `lib/facebookGraph.js`, which logs the method (GET/POST), path, status, duration, and a truncated response/error to an in-memory ring buffer (`lib/apiLogger.js`, last ~200 calls). View it at `/logs` — POST (write) calls are badged separately from GET (read) ones so the campaign-launch flow's writes are easy to pick out from the rest of the app's normal reads.

This is **best-effort only**: Vercel serverless functions have no persistent disk, so the log resets on cold start or redeploy. For a permanent record, use the Vercel dashboard's Function Logs for this project.

## Report caching

There are two layers of caching, both 30 minutes, both bypassed by the "Hard Refresh" button:

- **Server-side** (`lib/reportCache.js`): `/api/fb/report` caches its response per (user, ad account, exact date range) in-memory on the server for 30 minutes (same best-effort caveat as the API log — resets on cold start/redeploy).
- **Client-side** (`lib/clientCache.js`, used from `pages/report.js`): the browser also keeps every report payload it has fetched, keyed by (account, date range), for 30 minutes — in `localStorage`, not just in-tab memory, so it survives a page reload and is shared across tabs in the same browser, not lost the moment the tab closes. This means switching the date range selector — e.g. Last 7 Days → Last 30 Days → back to Last 7 Days — shows the already-fetched data instantly with **no network request at all**, not even a fast cache-hit one. A nice loading spinner shows only while an actual fetch is in flight (first load, a genuinely new range, or past the 30-minute TTL). `lib/clientCache.js` is a generic helper (not report-specific) — it's the one shared cache implementation other pages/tabs are expected to use too, rather than each inventing its own.

## Shared account selector

`components/AccountProvider.js` (mounted in `pages/_app.js`, above every page) is the single source of truth for "what Facebook data does this user have" — profile, Pages, and ad accounts — fetched once via `/api/fb/data` and cached for 30 minutes via `lib/clientCache.js`, instead of each page independently re-fetching it on mount (previously true of Dashboard, Report, and Strategy — three separate calls, with Strategy not even persisting the last-chosen account, unlike the other two). `useAccounts()` exposes `{ profile, pages, adAccounts, accountsLoading, accountsError, selectedAccountId, setSelectedAccountId, refreshAccounts }`. Because the Provider sits above `<Component>` and isn't remounted by client-side navigation, picking an account on one tab shows it already selected on another without any extra plumbing; `localStorage` additionally remembers it across sessions (same as before). The Provider gates its fetch on an authenticated session (`useSession()`), since the login page also renders through `_app.js`.

Strategy's own account dropdown is a superset of this (it also offers a "fresh/new account, no prior data" option with no real account id) and keeps that bespoke sentinel entirely local — only a real account selection there is written back into the shared `selectedAccountId`, so picking "fresh" on Strategy never leaks a non-existent account id into Dashboard or Report.

Dashboard's "Check ROAS" and Strategy's history-signal check now also cache their own per-account results through the same `lib/clientCache.js`/30-minute pattern, with Dashboard showing the same "loaded Xm ago · Hard Refresh" row (`components/CacheStatus.js`) that Report uses.

## Custom report builder (`/explore`)

The "Explore" tab (`pages/explore.js`) lets a user build any view of an account's Facebook Ads data themselves, rather than relying on the other tabs' fixed shapes: a date range (any preset up to 30 days, or Custom, cross-constrained to the cap), a level (Account/Campaign/Ad Set/Ad), one breakdown group, daily/weekly/no time grouping, a multi-select of metrics (plus a free-text raw-field escape hatch), and an optional compare-to-previous-period toggle — then an explicit **Run Query** button (nothing fires on every tweak, the whole point of this change being fewer redundant Graph API calls). Results render as a sortable/searchable table (`components/SortableTable.js` — a level's own name and a breakdown's value are always separate columns, e.g. "Ad" and "Age & Gender" side by side, never combined into one string where an ad's name would be indistinguishable from the breakdown value next to it; each metric's own column then shows its change — ▲/▼ and Δ% — directly under the value when comparing, rather than a separate column per metric off to the side) or a chart (`components/ExploreChart.js`, `recharts`, dynamically imported with `next/dynamic({ssr:false})` since it measures its container via `ResizeObserver` and can't be server-rendered): a time-grouped query without a breakdown draws a line/trend; a breakdown without time-grouping draws a bar chart ranked by whichever metric is picked to chart (capped to the top 20 rows); a time-grouped query *with* a breakdown pivots into one line per breakdown value (capped to 8 series); a single aggregate row with no breakdown/grouping has nothing to chart unless comparing to the previous period, in which case it's a simple 2-bar "then vs. now". Query results are cached the same way as everything else (`lib/clientCache.js`, 30 min, `<CacheStatus>` + Hard Refresh), keyed by the full query spec and pruned to the most recent 20 distinct queries so repeated experimentation doesn't grow `localStorage` without bound.

- **`lib/insightsMetrics.js`** is the catalog everything else is built from: `LEVEL_OPTIONS`, `BREAKDOWN_GROUPS` (curated, pre-combined, known-good breakdown combinations — e.g. "Age & Gender", "Platform & Placement" — **single-select, not a free multi-select of individual dimensions**, since Meta restricts which breakdowns can combine with each other and which are valid at which `level` in ways this app has no reliable way to pre-validate; offering pre-combined groups avoids producing mostly-400s), and `METRIC_CATALOG` (~25 metrics across Delivery/Engagement/Cost/Conversions/Video/Quality, each knowing its own underlying Graph field(s), how to extract its value from a raw insights row, and a display format — `formatMetricValue()` and `isChartableMetric()` key off that format so the table/chart always agree on how a metric reads and whether it can be plotted; "Quality" rankings are categorical text, table-only). `resolveGraphFields()`/`deriveRowMetrics()` translate between a chosen combination and Facebook's raw response shape.
- **`pages/api/fb/explore-insights.js`** (`POST`, not `GET`+query-string — the query spec doesn't fit cleanly in a URL, and this endpoint isn't meant to be HTTP/CDN-cacheable the way `/api/fb/report.js` is, since caching for it is handled entirely client-side) validates the request (date range capped at 30 days, `until` can't be in the future, at least one metric, level is a known value) and calls `graphGetInsights()` once for the requested period. An optional "compare to previous period" toggle (disabled together with daily/weekly time-grouping, since merging a time series against one prior-period aggregate is ambiguous) computes the immediately-preceding period of equal length and runs **both periods' Graph API calls in parallel** (`Promise.all`, not sequential awaits) — `graphGetInsights`'s async-job path can take up to its own ~15s poll timeout per call, and there's no reason two independent queries should serialize that cost. Previous-period rows are matched to current-period rows by a stable identity key (the level's own id plus every breakdown dimension's value) to compute a per-metric `_deltaPct`; a row with no prior-period counterpart gets `_previous: null`. A free-text "raw field name" escape hatch (`customFields`) passes any Graph API field straight through for anything not in the curated catalog.
- Can't log into a live Facebook account from this environment to test the real Graph API end to end — the backend was verified with a script exercising the actual shipped handler against a mocked `graphGetInsights` built from realistic response shapes (the ones `/api/fb/report.js`'s own working calls already use), covering every validation branch and confirming the two compare-to-previous-period calls really do run concurrently (timed against an artificial per-call delay) rather than one-after-another; the UI was verified in-browser the same way, with a mocked `/api/fb/explore-insights` response, across every table/chart combination described above.

## Known Graph API caveats

- **Insights queries can come back asynchronous, with no warning.** For large accounts in particular, Facebook will sometimes decide an `/insights` query (even a plain one with no breakdown) is too expensive to run synchronously and returns `{ report_run_id }` instead of `{ data: [...] }` — this is based on Facebook's own cost estimate for that specific request at that moment, not reliably predictable from the request shape, and is why the region/age-gender breakdowns could come back looking empty even though the account had data (a naive reader of `.data` just sees `undefined`). `lib/facebookGraph.js`'s `graphGetInsights()` wraps every `/insights` call used by the report, detects this, and polls the job (`/<report_run_id>`) until it completes, then fetches `/<report_run_id>/insights` for the real rows — transparent to the rest of the code. `vercel.json` raises `pages/api/fb/report.js`'s function timeout to 60s to leave headroom for this polling and for the pagination below.
- **Every list/insights call is paginated to completion, not just its first page.** `limit` only caps one page's size — Facebook still returns a `paging.next` cursor when more rows exist, and a caller that reads just `.data` silently gets a truncated result for any account bigger than one page. This was a real bug here: the ad-level insights query (`level: "ad"`, the single source of truth for every campaign/ad-set/ad number in the report) capped at `limit: 500`, so any account with more than 500 ads active in the selected range was missing ads from its structure tree, creative counts, and aggregated spend/revenue — everything downstream looked "off" without any error, because nothing failed, it just silently stopped at row 500. Fixed once, centrally: `graphGetInsights()` and the new `graphGetAllPages()` (for plain, non-insights list connections — campaigns, ad sets, custom audiences, Pages, ad accounts, pixels) both follow `paging.next` to completion via a shared `collectAllPages()` helper, capped at 50 pages (25,000 rows) as a runaway-loop safety net, not a real limit. This also covers a campaign's *nested* `adsets` edge, which has its own independent paging cursor — `fillTruncatedAdsets()` in `pages/api/fb/report.js` re-fetches the rest directly from `/<campaignId>/adsets` for any campaign whose first page wasn't the whole list.
- **Frequency is per-ad, not comparable across levels.** The High-Frequency Ads section shows each ad's own frequency over the selected range. Facebook deduplicates reach differently at the ad, ad set, and campaign level, so this will not match a campaign- or ad-set-level frequency column in Ads Manager — compare it against Ads Manager's own **per-ad** frequency for the same date range instead.
- **Bulk ad-level `reach`/`frequency` is unreliable past ~10 ads in one query — re-fetched in small chunks to correct it.** Confirmed live against a real account: the same ad, same date range, returns the correct `reach` (matching Ads Manager and a single-ad query exactly) when queried alongside 9 other ads, but querying it alongside just one more (11 total) in one `level=ad` request drops `reach` from ~205,000 to 721 and inflates `frequency` from 1 to ~285 — a hard cliff at exactly that boundary, not a gradual degradation. `impressions`/`spend`/`clicks` (plain sums) are unaffected; it's specifically the reach-deduplication computation that breaks down once too many ads are reach-computed together in one request — a known class of Facebook Marketing API limitation, not something fixable by changing how we read the response. `fetchAccurateFrequency()` in `pages/api/fb/report.js` re-fetches `frequency` in chunks of `FREQUENCY_CHUNK_SIZE` (10) ads at a time, filtered via `filtering: [{field: "ad.id", operator: "IN", value: [...]}]` (small enough to return synchronously, never triggering the async-job path), and overwrites the bulk value everywhere it's used (Account Structure, High-Frequency Ads). This is one extra Graph API call per 10 ads — for an account with many hundreds of active ads, a meaningful number of extra requests, accepted deliberately since a falsely-high frequency reading is indistinguishable from real creative fatigue and sends someone chasing a problem that doesn't exist.
- **Explicit date ranges, not `date_preset`.** The selected range (Today/Last 7 Days/Last 30 Days/Custom) is always sent as an explicit `since`/`until` pair rather than Facebook's `date_preset` shortcuts, since those can drift by a day from what Ads Manager's date picker shows — and reach-based metrics like frequency aren't additive across days, so even a one-day difference can visibly shift them. "Today" is the one exception that intentionally includes the partial, still-accumulating day — same as every other ad platform's "Today" view.
- **Creative thumbnails are fetched by exact ad ID, not via `/act_x/ads`.** That edge with no filter returns Facebook's default-ordered first N ads — oldest-created first — which for any account with real history is a completely different set from the ads with spend in the report window. `lib`-level code instead batches `?ids=<exact ad ids>&fields=creative{thumbnail_url,image_url}` (chunked by 50) against only the ad IDs actually shown in the report. Some ad formats (e.g. catalog/dynamic creative, Advantage+ flexible ads) still have no single static `thumbnail_url`/`image_url` and fall back to a blank placeholder — that's a real gap in what Facebook exposes for those formats, not a fetch bug.
- **`/search?type=adinterest` (ad-interest targeting search) takes exactly one `q` per call — no batch/bulk variant.** Resolving the ~50-80 AI-suggested names from Strategy 8's interest recommendations into real Meta interests means that many separate calls — `lib/metaInterestSearch.js`'s `mapWithConcurrency()` runs them through a small hand-rolled concurrency limiter (no new dependency) rather than either serializing all of them (too slow) or firing them all at once (risks Facebook rate limits and floods `/logs`).
- **Region/state breakdown carries spend but no purchase revenue — a Meta platform limitation, not a fetch bug.** Verified directly against a real account: the `breakdowns=region` call returns real per-state spend/clicks/engagement, but not a single row (out of 36 states, or 500+ ad×state rows at the ad level) carried a purchase action — `action_values` was entirely absent from (almost) every row — while the exact same account/range/fields with `breakdowns=age,gender` instead returns full purchase data. This matches Meta's documented restriction that Aggregated Event Measurement (the post-iOS 14.5 measurement model for web conversion events) excludes geographic breakdowns from the events it reports. It isn't something `graphGetInsights`'s async-job handling or any other fetch logic here can work around, since Facebook's response itself never contains the data — so `groupAndPareto()` takes a `metric` option (`"revenue"` default, `"spend"` for this one case) and the State section is a spend pareto instead of a revenue one.

## Environment variables

Copy `.env.example` to `.env.local` for local development, or set these directly in your Vercel project settings (Production/Preview/Development):

| Variable | Description |
| --- | --- |
| `FACEBOOK_APP_ID` | Facebook App ID (public) |
| `FACEBOOK_APP_SECRET` | Facebook App Secret (keep private — never commit) |
| `NEXTAUTH_SECRET` | Random string used to sign session tokens. Generate with `openssl rand -base64 32` |
| `NEXTAUTH_URL` | The deployed URL (e.g. `https://your-app.vercel.app`). Not required on Vercel in production (auto-detected), but needed for local dev. |
| `OPENROUTER_API_KEY` | OpenRouter API key (keep private — never commit), used by Strategy 8's AI interest-recommendation step (`lib/openrouter.js`) |
| `OPENROUTER_MODEL` | Optional — overrides the default Gemini model slug called via OpenRouter (defaults to `google/gemini-2.5-flash`). OpenRouter's model strings change over time; bump this instead of editing code |
